ПОС, преподавательская оценка студентов. Консольное приложение на Python: заводит студентов
и критерии, выставляет оценки, считает итог по весам и выгружает его в CSV.

Скрябин Андрей Дмитриевич, БПИ258

# Запуск

```
python -m pip install -r requirements.txt
python main.py
python -m pytest --cov
```

Меню:

```
1. Добавить студента
2. Добавить критерий        (название, максимальный балл, вес)
3. Студенты и критерии
4. Выставить оценку
5. Исправить оценку
6. Отменить оценку
7. Все оценки
8. Итоги
9. Правило итога            (по всем критериям или только по выставленным)
10. Экспорт итогов в CSV
11. Демо                    (сквозной сценарий на пустых данных)
0. Выход
```

Пункт 11 проходит весь путь: студенты и критерии, оценки, попытки нарушить правила, исправление
и отмена, итог по двум правилам, экспорт в `demo_final_grades.csv`.

# Логика решений

Итог считается как взвешенная доля от максимума, переведённая в 10-балльную шкалу:
сумма `балл / максимум × вес` делится на сумму весов и умножается на 10. Итог нигде не хранится
и считается заново при каждом запросе, поэтому он всегда совпадает с текущими оценками.

У студента по одному критерию одна оценка. Вторую поставить нельзя, существующую можно исправить
или отменить. Удаление студентов и критериев не делал: в задании оно не обязательно, а удаление
критерия, по которому уже есть оценки, потребовало бы отдельных правил.

Данные хранятся в памяти. Хранение спрятано за портами-репозиториями, поэтому файл или базу
можно подключить новым адаптером, не трогая домен.

# Карта DDD

Слова из задания совпадают с именами в коде:

```
студент      Student                 entity, корень агрегата       src/domain/student.py
критерий     Criterion               entity внутри рубрикатора     src/domain/rubric.py
рубрикатор   Rubric                  корень агрегата               src/domain/rubric.py
оценка       Evaluation              value object                  src/domain/values.py
балл         Score                   value object                  src/domain/values.py
итог         FinalGradeCalculator    domain service                src/domain/grading.py
```

Entity и value object. `Student` это entity: его узнают по номеру (`id`), а не по полям.
Два студента «Иванов» с разными номерами считаются разными людьми, а оценки одного студента
со временем меняются, но студент остаётся тем же. Поэтому `Student.__eq__` сравнивает только `id`.
`Score` это value object: у балла нет своей личности, `Score(7) == Score(7)`, и его нельзя изменить
(`frozen=True`). `Evaluation` тоже value object, это неизменяемый факт «по критерию поставили
такой балл такого числа». Исправление не меняет старую оценку, а заменяет её новой.

Агрегаты. Их два. `Rubric` владеет критериями: выдаёт им номера и не даёт завести два критерия
с одинаковым названием. `Student` владеет своими оценками: не даёт поставить вторую оценку
по тому же критерию, исправить или отменить несуществующую. Между собой агрегаты связаны
только номером критерия (`Evaluation.criterion_id`), а не ссылкой на объект.

Инварианты и где их охраняют:

```
балл не меньше 0 и это число       Score.__post_init__
балл не больше максимума критерия  Criterion.check, вызывает EvaluationFactory
оценка только по критерию          Rubric.criterion, вызывает EvaluationFactory
  из рубрикатора
одна оценка на критерий            Student.evaluate
максимум и вес больше 0            Criterion.__init__
итог согласован с оценками         FinalGradeCalculator.final_grade
```

Repository. Порты `StudentRepository` и `RubricRepository` лежат в домене
(`src/domain/repositories.py`), реализации в памяти лежат в инфраструктуре
(`src/infrastructure/memory_repositories.py`).

Domain service. Итог зависит сразу от двух агрегатов: от оценок студента и от весов рубрикатора.
Ни одному из них это правило целиком не принадлежит, поэтому оно вынесено в
`FinalGradeCalculator`. Он же проверяет, что у студента нет оценок по критериям вне рубрикатора,
и округляет итог до сотых.

# Архитектура

Ports and Adapters (гексагональная), три слоя-папки:

```
src/
  domain/          сущности, value objects, инварианты, domain service, порты репозиториев
  application/     сценарии (PosFacade) и порт экспорта GradeExporter
  infrastructure/  адаптеры: репозитории в памяти, CSV-экспорт, консоль, демо
  container.py     composition root: DI-контейнер собирает граф
main.py            запуск
```

Зависимости направлены внутрь:

```
infrastructure  ──>  application  ──>  domain
       └──────────────────────────────>  domain
container.py знает все слои и собирает их вместе
```

Домен не импортирует ничего из других слоёв и ничего не знает про консоль, CSV и `punq`.
Приложение не знает про инфраструктуру и работает с портами `StudentRepository`,
`RubricRepository` и `GradeExporter`. Это проверяет `tests/test_architecture.py`.

# Паттерны GoF

Порождающий: фабрика `EvaluationFactory` (`src/domain/evaluation_factory.py`). Единственное место,
где создаётся оценка. Без неё каждый сценарий (выставить, исправить) сам искал бы критерий в
рубрикаторе, проверял диапазон и ставил дату, и достаточно было бы забыть одну проверку, чтобы
поставить 12 из 10. Фабрика делает это за один вызов, поэтому неправильную оценку через
приложение не получить.

Структурный: фасад `PosFacade` (`src/application/facade.py`). Консоль вызывает один объект с
понятными методами (`put_evaluation`, `final_grades`, `export_final_grades`) и не знает про
репозитории, фабрику, калькулятор и экспорт. Без фасада порядок «достать студента, создать оценку
через фабрику, применить к студенту, сохранить» был бы размазан по меню и повторён в демо.

Поведенческий: стратегия `FinalGradeRule` (`src/domain/grading.py`). Правило итога можно менять
прямо в работающей программе (пункт 9 меню). `WeightedSumRule` считает невыставленную оценку
нулём, это итоговая оценка за курс. `GradedOnlyRule` учитывает только выставленные, это текущая
успеваемость посреди семестра. `FinalGradeCalculator` не меняется при добавлении нового правила,
например «с порогом» или «с бонусом»: достаточно нового класса-наследника и строки в `RULES`
в `console_app.py`.

# DI-контейнер

`src/container.py` на `punq`. В нём сказано, какая реализация стоит за каждым портом:
`StudentRepository` за `InMemoryStudentRepository`, `GradeExporter` за `CsvGradeExporter`,
`FinalGradeRule` за `WeightedSumRule`. Репозитории, калькулятор и фасад зарегистрированы как
singleton, чтобы консоль и демо работали с одними и теми же данными. В тесте
`test_container_fake_exporter` экспорт подменяется на `FakeExporter` одной строкой
`container.register(GradeExporter, instance=fake)`.

# Тесты

57 тестов, покрытие 100 %. `tests/test_domain.py` проверяет инварианты: балл выше максимума,
отрицательный балл, несуществующий критерий, вторая оценка, равенство entity по номеру и
value object по значению. `tests/test_grading.py` проверяет domain service и обе стратегии,
включая то, что итог меняется после исправления и отмены оценки. `tests/test_facade.py` проверяет
сценарии с подставным экспортом, `tests/test_console_app.py` проверяет меню, неверный ввод и демо.
